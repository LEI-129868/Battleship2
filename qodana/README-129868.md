## Teste do quality gate

Pull request utilizado:
[PR #16](https://github.com/LEI-129868/Battleship2/pull/16).

### Execução com falha

[Execução com duplicação intencional](https://github.com/LEI-129868/Battleship2/actions/runs/41837690508).


Foram mantidas duas cópias do método buildMap em BoardWindow.java.
O relatório identificou três fragmentos iguais, começando nas linhas
93, 125 e 157 dessa versão do ficheiro, agrupados num problema DuplicatedCode.
Com severityThresholds.any: 0, o quality gate falhou.
Previamente ainda foi feito outro teste em que, para o mesmo numero de fragmentos
duplicados, aumentou-se o severityThresholds.any para 3 e para este caso o 
relatório apresentou os mesmos probelmas de código duplicado mas o 
quality gate não falhou.

### Execução com sucesso

[Execução após a correção](https://github.com/LEI-129868/Battleship2/actions/runs/41839924934).

No commit 0382a94 foram removidos os métodos buildMap1 e buildMap2,
mantendo o método original.
O relatório passou a apresentar zero problemas e o quality gate passou.

## Reflexão

A ferramenta detetou a duplicação introduzida deliberadamente e deixou
de a reportar após a remoção das cópias.
Neste teste não identifiquei falsos positivos, mas a ausência de resultados
no código original não permite excluir falsos negativos.
O limiar por omissão de 45 unidades condiciona o tamanho mínimo
dos fragmentos detetados, enquanto any controla os problemas
admitidos: a ocorrência foi aceite com any: 3 e rejeitada com any: 0.
Esta inspeção aproxima a estratégia Significant Duplication do livro,
mas não reproduz diretamente as condições combinadas de SEC, LB e SDC
nem os seus limiares relativos.
