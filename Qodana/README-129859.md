# Qodana Quality Gate — Large Class

**Aluno:** Daniel Silva  
**Número:** LEI-129859

## Tabela de mapeamento

| Cheiro do catálogo de Fowler | Inspeção no IntelliJ IDEA | ID da inspeção | Métrica e limites | Limitações |
|---|---|---|---|---|
| Large Class | Class with too many methods | `MethodCount` | Número de métodos por classe. Limite por omissão: 20. Limite experimental utilizado: 30; são assinaladas classes com mais de 30 métodos. | Aproxima o cheiro apenas pela contagem de métodos. Não combina essa contagem com WMC, TCC ou ATFD e não avalia a distribuição de responsabilidades da classe. |

O cheiro escolhido é **Large Class**. A configuração final substitui a tentativa anterior de detetar Data Class por uma inspeção disponível no Qodana for JVM.

## Configuração utilizada

| Elemento | Configuração |
|---|---|
| Workflow | `.github/workflows/qodana-129859.yml` |
| Configuração do linter | `qodana-129859.yaml` |
| Perfil de inspeção | `.qodana/profiles/profile-129859.yaml` |
| Qodana Action | `JetBrains/qodana-action@v2026.2.2` |
| Linter | `jetbrains/qodana-jvm:2026.2` |
| JDK do projeto | 21 |
| Inspeção ativa | `MethodCount`, com severidade `ERROR` |
| Limite de métodos | `m_limit: 30` |
| Getters e setters | Incluídos: `ignoreGettersAndSetters: false` |
| Métodos sobrescritos ou implementados | Incluídos: `ignoreOverridingMethods: false` |
| Âmbito da inspeção | Ficheiros Java em `src/**/*.java` |
| Condição de falha | `failureConditions.severityThresholds.any: 0` |
| Check individual | `large-class` |

O workflow executa em pull requests para `main`, em pushes para `main` e por execução manual. A opção `pr-mode: false` permite analisar o projeto completo, em vez de restringir os resultados às alterações do pull request.

O perfil é carregado através de `imports`, desativa as restantes inspeções e ativa `MethodCount`. O token é fornecido pela variável de ambiente `QODANA_TOKEN`, cujo valor é obtido de um secret do repositório.

O valor 30 é um limite experimental usado neste projeto, não um limiar atribuído ao livro *Object-Oriented Metrics in Practice*. Na execução sem a classe de teste, esta configuração não produziu ocorrências da inspeção selecionada.

O limite da inspeção e a condição de falha têm funções diferentes: `m_limit: 30` determina quais as classes assinaladas; `any: 0` faz reprovar o job quando existe pelo menos uma ocorrência. Permitir uma ocorrência com `any: 1` faria passar uma análise com um único problema, sem alterar a deteção do cheiro.

### Cheiro provocado

No commit [`e3333b7`](https://github.com/LEI-129868/Battleship2/commit/e3333b7db7da3dbf5ce50e5e3324bbeb7b1ca851), foi adicionado o ficheiro `src/main/java/battleship/LargeClassProbe.java`, com 31 métodos. A classe ultrapassou o limite de 30 e a execução terminou com uma ocorrência de **Class with too many methods**, fazendo falhar o job `large-class`.

### Correção

No commit [`f44e12a`](https://github.com/LEI-129868/Battleship2/commit/f44e12aaf2bcd8fef7edacb91a6c4ea4ccb73155), a classe criada apenas para o ensaio foi removida no mesmo ramo e pull request. A execução seguinte terminou com zero ocorrências da inspeção selecionada e o job passou.

## Reflexão

A inspeção identificou a classe de teste com 31 métodos e deixou de produzir ocorrências após a sua remoção.
Uma contagem isolada pode produzir falsos positivos em classes com muitos métodos simples e falsos negativos em classes com poucos métodos muito complexos.
Aumentar o limite de métodos reduz a sensibilidade da deteção, enquanto aumentar o número de problemas permitido pelo gate pode fazer passar uma análise que continua a conter ocorrências.
Esta configuração usa um limite absoluto e uma única métrica, pelo que não reproduz as estratégias compostas nem os critérios relativos apresentados no livro.
