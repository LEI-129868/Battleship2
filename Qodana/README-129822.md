## Tabela de Mapeamento

| Cheiro (Fowler) | Inspeção no IDE | ID da inspeção | Métrica / limiar por omissão | Limitações |
|---|---|---|---|---|
| Long Parameter List | Method with too many parameters | `ParametersPerMethod` | Número de parâmetros (`m_limit`): 5 por omissão | Limiar absoluto fixo; não avalia o contexto do sistema (média e desvio-padrão) nem combina diretamente com outras métricas. |

## Referências do Livro

*Object-Oriented Metrics in Practice* (Michele Lanza e Radu Marinescu):
- **Páginas 13–18:** Discussão das métricas e estabelecimento de valores-limite estatísticos (Tabela 2.2).
- **Métricas ao nível de método:** Métrica **NOPM** / **PAR** (*Number of Parameters*), onde se discute o impacto negativo de métodos com excesso de parâmetros na compreensão, acoplamento e facilidade de teste do software.

- **JDK do projeto:** `21`

O perfil YAML `.qodana/profiles/profile-129822.yaml` utiliza a base `empty`, garantindo que apenas a inspeção `ParametersPerMethod` é executada. Desta forma, o Quality Gate atua especificamente sobre a deteção de métodos com listas longas de parâmetros sem interferência de regras secundárias.

## Teste do Quality Gate

Pull Request utilizado:
- [PR #30](https://github.com/LEI-129868/Battleship2/pull/30)

### Execução com Falha (Deteção do Cheiro)

- [Execução com o code smell provocado ](https://github.com/LEI-129868/Battleship2/actions/runs/42402846909/job/128494163167?pr=30)

No ramo `teste2-long-parameter-list`, foi introduzido deliberadamente no ficheiro `src/main/java/battleship/Main.java` o método `testeLongParameterList` com 6 parâmetros:
```java
public static void testeLongParameterList(int a, int b, int c, String d, String e, double f) {
    // Método com 6 parâmetros para provocar o erro no Qodana
}
```
Como o limiar estava parametrizado para `m_limit: 5`, o Qodana assinalou 1 problema de severidade `ERROR`. Com a regra de qualidade `severityThresholds.any: 0`, o Quality Gate falhou a vermelho como esperado.

### Execução com Sucesso (Após Correção)

- [Execução após correção ](https://github.com/LEI-129868/Battleship2/actions/runs/42403315269/job/128495581541?pr=30)

Após a confirmação da deteção e da falha do Quality Gate, o método temporário com excesso de parâmetros foi removido de `src/main/java/battleship/Main.java`. Na nova análise executada pelo GitHub Actions, o Qodana não reportou qualquer violação e o Quality Gate terminou com sucesso (verde).

## Reflexão

A ferramenta Qodana detetou com precisão a ocorrência introduzida deliberadamente no método `testeLongParameterList`, indicando a localização exata do método em `Main.java` e deixando de a assinalar após a remoção do mesmo. Não foram observados falsos positivos no restante código da aplicação com o limiar configurado para 5 parâmetros, embora possam surgir em casos pontuais legítimos, tais como construtores ou métodos de injeção de dependências múltiplas. O resultado revelou-se estritamente dependente da sensibilidade do limiar configurado (`m_limit`): métodos com até 5 parâmetros são permitidos, enquanto 6 parâmetros provocam a rejeição imediata quando o limiar de aceitação é zero (`any: 0`). Relativamente às limitações face à abordagem do livro *Object-Oriented Metrics in Practice*, a inspeção do Qodana assenta num valor de corte estático e absoluto, não refletindo a distribuição estatística do sistema (como a média e desvio-padrão propostos por Lanza e Marinescu) nem combinando de forma lógica o número de parâmetros com outros fatores, como o acoplamento ou a complexidade ciclomática do método.
